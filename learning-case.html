01 / THE BUSINESS QUESTION

Which components put the plan at risk?

A fictional planner needs to check whether available material covers a three-product production plan. The BOM gives the quantity of each component per product. The planner also needs demand, inventory, reservations, and unit costs to understand the shortage exposure.

  1. BOM: what parts each product needs, and how many.
  2. Demand: how many finished products the plan calls for.
  3. Inventory: how much stock is on hand and already reserved.
  4. Part costs: a consistent basis for estimating shortage value.
  5. Decision: investigate constrained components and affected products, then confirm stock, purchase-order timing, and planning priorities with the owners.

This is one flat, single-level snapshot. It does not model dated supply, alternate parts, scrap, safety stock, multi-level BOMs, or a feasible production allocation.

03 / FOLLOW ONE NUMBER

Why component C01 is short by 80.

Required quantity

FG-A needs 2 brackets each, and demand is 40 units. FG-B needs 3 brackets each, and demand is 30 units.

Required C01 = (40 × 2) + (30 × 3) = 170

Aggregate the requirement across all products before comparing it with stock. Otherwise the same stock could be counted more than once.

Availability and exposure

C01 has 100 on hand and 10 reserved. This leaves 90 available against the combined requirement.

Available = 100 − 10 = 90
Shortage = max(170 − 90, 0) = 80
Shortage value = 80 × $12 = $960

C05 adds another $500 of shortage exposure. The base snapshot therefore totals $1,460.

04 / THE TECHNICAL ROLES

What each tool contributes.

Python — validate and calculate

Python checks the synthetic input, consolidates component requirements, subtracts reservations, and calculates shortages and exposure. The local prototype rejects unknown references, duplicate BOM lines, invalid quantities, and inconsistent stock values.

required[component] += product_demand * quantity_per
available = on_hand - reserved
shortage = max(required - available, 0)
shortage_value = shortage * unit_cost

The prototype has focused technical tests. These check calculation behavior; they are separate from business acceptance testing.

Django — expose the calculation as a local API

Django provides a read-only HTTP endpoint so another application can request the calculated snapshot as JSON. This keeps the business rule in one place rather than copying spreadsheet logic into multiple reports.

GET http://127.0.0.1:8770/api/kpis/
→ component requirements, shortages, product exposure, KPI totals

The included service is a local educational prototype with synthetic inputs. It does not include production authentication, an ERP connection, a managed database, scheduling, or a deployed Azure environment.

Power BI — proposed report design
DESIGN GUIDE · NOT A DEPLOYED POWER BI REPORT

The proposed report imports the consolidated component KPI table from the local API or an exported snapshot. One component appears once in that table. Cards show the shortage count and exposure value; a table shows the constrained components. A business owner would agree the refresh timing, metric definitions, filters, and permissions before production use.

Illustrative Power Query import for the local service:

let
    Source = Json.Document(Web.Contents("http://127.0.0.1:8770/api/kpis/")),
    Components = Table.FromRecords(Source[components])
in
    Components

After naming that imported table ComponentKPI, the proposed DAX measures are:

Short Parts =
COUNTROWS(FILTER(ComponentKPI, ComponentKPI[shortage_qty] > 0))

Shortage Value =
SUMX(ComponentKPI,
    ComponentKPI[shortage_qty] * ComponentKPI[unit_cost])

These are design examples. No .pbix report, Power BI refresh configuration, or Power BI Service publication is included.

Azure DevOps — proposed delivery workflow
PREPARED WORKFLOW · NO AZURE DEVOPS BOARD USED

The prepared backlog separates the calculation, shortage interpretation, and KPI explanation into small stories. In Azure Boards, these could be refined with a Product Owner, linked to tasks and test evidence, and tracked through the team’s delivery process.

Suggested sequence: intake → refinement → prioritization → development → technical testing → agreed business UAT → authorized release decision → stabilization. This is a learning workflow, not a claim of prior Agile or Azure DevOps delivery.

Example story: As a planner, I want component requirements combined across products so that shared stock is not counted separately against each product.

Example acceptance criterion: at base demand, C01 required quantity must equal 170 before comparison with available stock. Unknown references and duplicate product-component rows must be rejected.
